## Found 2026-09-29 — from www-chiddingfoldbonfire CI (security)

| # | Where | Issue |
|---|---|---|
| M-03 | util `ci/infisical.go` `infisicalLogin` + `gitlab/clog.gitlab-ci.yml` + `clog ci` help | **Tricky security bug that creeps in silently: an Infisical OIDC identity's Subject pattern goes wrong and nothing tells you why.** Seen 2026-09-28/29: every bonfire deploy got `HTTP 403: Access denied: OIDC subject not allowed.` A hand edit on 2026-09-23 (fixing the prod nightly) had (a) pasted the new subject onto the END of `gl-mrmxf-dev`'s pattern (`…:ref_type:*:ref:ref_type:branch:ref:main`, matches nothing) and (b) REPLACED `gl-mrmxf-prod`'s `v*` tag subject with the `main` one, so release tags lost prod secrets while the nightly kept working. It went unseen for 5 days. The 403 is identical for every cause, the Infisical console shows what was meant rather than what matches, and the audit log that shows the received `sub` is not on every plan. The two identities are shared by `clog-mrmxf` and `www-chiddingfoldbonfire`, so one bad edit breaks several repos, and the "fix" people reach for under pressure is to widen the pattern (e.g. `ref:*` on prod), which hands prod secrets to any branch. **Handle it in clog so the fix propagates to every repo on a pin bump, instead of each repo carrying its own workaround** (bonfire's `.gitlab-ci.yml` deploy job now decodes `$INFISICAL_ID_TOKEN` with base64+jq as a stopgap; remove it once clog does this). (1) On a failed login, `infisicalLogin` decodes the JWT **payload only** (never log the token, it is a live credential) and adds `sub`, `aud`, `ref_type`, `ref`, `ref_protected` to the error, so the log says exactly what the Subject must match. (2) A `clog ci oidc subject` (name open) that prints the subject this run will present and, per identity in `ci.infisical.identity`, the canonical pattern clog expects: dev `project_path:<group>/{<p1>,<p2>}:ref_type:*:ref:*`, prod `project_path:<group>/{<p1>,<p2>}:ref_type:{tag:ref:v*,branch:ref:main}` — one brace glob, no top-level commas, no spaces; Subject field, not Claims. Generated from `.clog.yaml`, so the text people paste into Infisical comes from config, not memory. (3) Optionally warn when the prod pattern would accept a non-protected ref. Lands in util `ci` (tag `ci/vX.Y.Z`), then a pin bump here, then the stopgap comes out of each repo. |

## Found 2026-10-03 — from cloudflare-workers `cli-tools/bucket-bucket` (b2b archive tool)

| # | Where | Issue |
|---|---|---|
| M-04 | util `slogger/pretty-with-dbg-tmp-handler.go` `DbgTmpLogPath` (:16) + `newDbgTmpHandler` (:44) | **The shared `/tmp/clog-YYYY-MM-DD.log` locks out every user but the first each day.** `newDbgTmpHandler` creates the file with `0644`, so whoever runs any clog command first that day (yourself, root via `sudo`, a service user) owns it, and every other user's clog falls back to console only: `WRN debug log unavailable, console only path=/tmp/clog-2026-10-03.log err=open ...: permission denied`. Seen 2026-10-03 on the b2b archive instance: the `b2b` service user lost its JSON debug log because another user had run clog first. It is per-day and order-dependent, so it comes and goes and looks random. Opening the file `0666` would "fix" it, but then any local user can forge lines in everyone's log, so don't. **Fix:** make the path per-user, e.g. `/tmp/clog-<user>-YYYY-MM-DD.log` (`os/user.Current().Username`; fall back to the uid if lookup fails), keep `0644` and keep the warning. Update the `DbgTmpLogPath` doc comment, `StylePrettyWithDbgTmp` in `slogger.go` and any help that names the old path, and add a test that two different users' paths differ. Lands in util `slogger` (tag `slogger/vX.Y.Z`), then a pin bump here. **Downstream:** `cloudflare-workers/cli-tools/bucket-bucket/bucket2bucket.sh` works around this by sending clog's JSON to `$B2B_LOG_DIR/clog-<user>/` via `TMPDIR`. Once this lands it can go back to `/tmp` if wanted, but its `collect_clog` must then look for the new per-user file name. |
